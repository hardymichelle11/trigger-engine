# Session Notes — 2026-05-05

## Session 36: Remote-access exploration (Firebase Hosting experiment, rolled back)

### Goal
Originally a bug-triage session: user reported (a) the **LB button on mobile is not working**, and (b) the **engine is not generating output correctly**. Conversation pivoted to the broader question of how to access the app remotely (mobile, away from the dev laptop), which led to a Firebase Hosting trial deployment to validate the path before committing.

### What was attempted
1. **Wiring inspection for the LB-on-mobile bug** — `main.jsx:195` passes `onOpenLethal={() => setPage("lethal-board")}` to `<App>`; `App.jsx:705` destructures it; `App.jsx:930` renders the mobile button with that handler; `App.jsx:846-847` flips `.left-panel` ↔ `.left-panel-mobile` at the 1024 px breakpoint. **No defect identified from code review alone** — needs a specific repro from the user (missing button vs. dead click vs. broken target page).
2. **Hosting options compared** — Cloudflare Pages, Firebase Hosting, GCS+CDN+LB, Firebase in a separate GCP project. User declined Cloudflare Pages on a constraint preference and chose Firebase, conditioned on minimizing disruption to the live Trigger Engine.
3. **Firebase Hosting scaffolded** in the repo (`.firebaserc`, `firebase.json`) and deployed to the existing `aipicks-stock` Firebase project. Verified deploy at `https://aipicks-stock.web.app`. Confirmed the gate-page (`ApiKeyGate`) renders correctly in production.
4. **Rolled back the deploy** at the user's request — `firebase hosting:disable --project aipicks-stock` restored the "Site Not Found" placeholder; all four scaffolded files (`firebase.json`, `.firebaserc`, `public/_redirects`, `public/_headers`) and the `.firebase/` cache were deleted. `git status` confirms repo is back to pre-session state (only the four pre-existing untracked items remain).

### Decisions made
- **No code changes shipped.** The original bugs (LB-on-mobile, engine output) were not investigated to root cause because the user did not provide repro details, and the conversation moved to hosting before triage could continue. Both are captured in `WORK_QUEUE.md` for the next session.
- **Firebase project `aipicks-stock` left alive on Spark plan** — deletion has a 30-day cooldown that locks the project ID; cheaper to leave dormant than to lose the option to redeploy quickly.
- **Empty GCP project `my-project-trigger-engine-lb` left alive** — created during the experiment but never wired to Firebase; flagged for cleanup in `WORK_QUEUE.md` (not urgent — empty projects don't bill).
- **Production runtime services flagged as blockers for any future remote deploy**: KnowledgeBot Express server has no production host, ThetaData Terminal is local-only by design, BQ read proxy doesn't exist (`VITE_BQ_PROXY_URL` would be empty at build time). Captured in `WORK_QUEUE.md` "Hosting / Deploy" section so the next deploy attempt doesn't rediscover them.
- **Memory write skipped** — auto-memory for this session writes to the `my-app` memory store (working directory is locked for the session), but the only durable preferences surfaced were "be cautious about disrupting Trigger Engine" and "dislikes Firebase's GCP-coupling on deletion". Both are situational enough that I noted them in the session log instead of as standalone memories.
